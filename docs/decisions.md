## D-01 実行基盤は Cloudflare Workers（2026-11-02）
Workers + Hono（TypeScript）。データは D1、画像は R2（非公開）。無料枠で動き、宿ごとのサーバー管理が不要なため。

## D-02 デプロイは Cloudflare の Git 連携（2026-11-02）
GitHub の main に push すると Workers Builds が自動デプロイする。開発環境（クラウドのコンテナ）からは Cloudflare API に接続できないため、`wrangler deploy` を手元で実行しない構成にする。
2026-11-02 初回デプロイ成功：https://qr-yado.rutsunom.workers.dev （workers.dev と preview URL を明示的に有効化）
2026-11-02 追記：この時点では Git 連携が未設定だったため、16時台に設定した。設定後の最初の push（b8f964a）で自動デプロイの成功を確認した。

## D-03 印刷は AirPrint ＋ Webページ（2026-11-02）→ D-10 で変更
宿主用の印刷ページを iPad のブラウザで開き、AirPrint で手元の Canon／ブラザーのレーザープリンターに出す。
- 通常のWebページからは印刷ダイアログを省略できない（省略できるのは専用キオスクアプリか自作アプリのみ）
- 自作アプリの直接印刷 API（UIPrintInteractionController.print(to:)）は iPadOS 27 で2件目以降が無言で失われる不具合が報告されている
- そのため「大きなボタン1つ＋ダイアログで印刷」の2タップ方式にする。メールプリントは使わない

## D-04 決済は現金のみ（2026-11-02）→ 受領の記録は D-15 で変更
請求額はシステムで計算し、受け取りは紙の受領欄と宿主用ページのボタンで記録する。

## D-05 税率はデータとして持つ（2026-11-02）
10%・8%・1%（2027/4〜、法律未成立）が期間で混在するため、区分・税率・適用期間のテーブルで管理し、コードに直接書かない。

## D-06 Claude と通常コードの役割分担（2026-11-02）
Claude：パスポート・レシートの読み取り、勘定科目の分類、多言語化、問い合わせの分類。出力は JSON schema で検証し、人が確認する画面を挟む。
通常コード：金額・税額・日数の計算、定期報告の集計、上限判定。

## D-07 個人情報の扱い（2026-11-02）
本物のパスポート・レシートはリポジトリにも動画にも入れない（見本・架空データのみ）。宿に置く紙には旅券番号を載せない。旅券の写しは非公開の R2 に保存。

## D-08 外部 API（2026-11-02）
- 国税庁 インボイス公表システム Web-API（ID取得済み）：レシートの登録番号照会に使う。ID は secret で管理
- freee：まず取込用 CSV を出力する。API 連携は余裕があれば

## D-09 宿泊者名簿の記載事項（2026-11-02）
住宅宿泊事業の名簿項目は「氏名・住所・職業・宿泊日」、日本に住所のない外国人は「国籍・旅券番号」も必須として設計する。旅館業法で職業に代わって入った「連絡先」は、住宅宿泊事業の必須項目としては扱わない。
- 確認した根拠：住宅宿泊事業法施行規則第7条、和歌山県・京都市・川崎市の案内。愛媛県・宇和島市の案内は未確認で、実運用前に確認する
- 外国人宿泊者は旅券の写しを保存する。写しの保存で氏名・国籍・旅券番号の記載を代替できるが、本システムでは集計にも使うためデータとしても持つ
- 住所・職業は旅券の読み取りでは埋まらない前提で、宿泊者の入力欄を設ける
- 名簿は作成から3年保存する

## D-10 印刷は宿泊者のチェックインを起点に自動で出す（2026-11-02）
宿主の操作はなくす。チェックイン完了でサーバーの印刷待ちに入れ、宿の機器が取りに来て印刷する。D-03 の「宿主が iPad で2タップ」は、スマホを使えない宿主には負担が残るため変更する。
- デモ：手元の Mac と Canon／ブラザーのレーザーで動かす
- 本番：Star CloudPRNT などのクラウド対応プリンターを検討（価格・納期は未確認）
- 予約と本人確認が済んだときだけ印刷する（玄関のQRは写真でも読めるため）
- 紙が出ないときは、宿泊者のスマホに大きな日本語の案内を出し、運営者に通知する。iPad は予備

## D-11 紙は1人1泊につき1枚（2026-11-02）
紙が交流のきっかけであり、宿の帳簿の土台でもある。翻訳アプリでは代わりにならない。
- 載せる：事前登録の顔写真、カタカナ読みの名前、金額、現金受領欄、宿泊者の署名欄
- 載せない：旅券番号、旅券の写し（D-07）
- 署名した紙の束を宿の宿泊台帳の原本とし、1か月ごとの一覧も印刷する
- 法定の宿泊者名簿は電子で作成・保存する。住所・職業・国籍・旅券番号を持ち、旅券の写しとともに3年保存する（施行規則第7条：電磁的記録は紙に出力できれば可）
- 同じ印刷番号では二重に印刷しない
- 布団のそばに置く名札は別紙で検討中（載せる項目は未定）

## D-12 名前のカタカナ読みは Claude が作る（2026-11-02）
欧州の多言語の名前は、綴りだけでは読めない。国籍や言語も手がかりに Claude が読みを作り、JSON schema とカタカナの文字種で検証する。宿泊者本人が直せるようにする。

## D-13 四国全体の需給ダッシュボードを MVP に入れる（2026-11-02）
現在は市町村ごとに分かれ、四国全体の詰まりを感知できない。これをサプライチェーンの問題として解く。
- 初回の受付は60日前、翌々日の宿は当日正午に自動で割り当てる
- 「区間×日付」で需要と宿の容量を比べ、足りなければ受付にブレーキをかけ、公民館・集会所の臨時開放を候補として示す
- 宿と需要は架空データであることを明示する。計算は通常のコードで行い、Claude は依頼文と告知文の下書きを担う
- 地図データ：地理院タイル（背景）、OpenStreetMap（遍路ルート、ODbL）、国土数値情報 P05（公民館・集会所、CC BY 4.0）
- Google Places は当面使わない（緯度経度の保存は30日まで、Google 以外の地図と併用不可）

## D-14 飲食店は宿主の電話でつなぐ（2026-11-02）
飲食店の予約機能はあえて作らない。宿に3,000円程度のプチ豪華めしの案内を置き、宿泊者から依頼があれば宿主が電話で店につなぐ。地域のつながりを増やすことを優先する。

## D-15 現金の記録と運営の単位（2026-11-02）
宿は地域の5人程度で運営する。1人では病気のときが不安で始められないため。現金は宿ごとのお財布で管理する。
- 受領の記録：宿泊者がスマホで「支払った」を押し、紙の受領欄を原本とする。宿主の操作はなくす
- 標準は1軒の空き家を5人程度で回す形。各自の自宅を組にする形や、5人で2軒の形にも対応する。データは「運営グループ」と「宿」を分け、1グループが複数の宿を持てるようにする
- 売上・経費・残高は運営グループのお財布で管理し、記録には宿も持たせる。コードで出す残高と実額を月ごとに照らし合わせる（お財布を宿ごとに分けたい場合は要確認）
- 年180日の上限は宿ごとに判定する
- 未決：届出の名義（連名、法人）、当番制が家主不在に当たるか、管理業者への委託、5人への利益の分け方と確定申告。実運用前に行政・商工会に確認する

## D-16 主キーに旅券番号を使わない（2026-11-02）
旅券番号は発行国の中で文書を識別するもので（ICAO Doc 9303）、更新で変わることもある。さらに個人情報でもある。
- 宿泊者・宿泊・印刷にはランダムな ID を主キーとして振る
- 旅券番号は発行国コードとの組で保存する。読み違いでチェックインが止まらないよう、重複は一意制約で弾かず警告にする
- 「1人1泊1枚」は DB の一意制約で守る（宿泊者×宿泊日、宿泊×印刷）
- 旅券の読み取り結果は、機械読取欄のチェックディジットをコードで検算する（D-06）
